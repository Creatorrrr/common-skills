## 1. 핵심 결론

세 시스템의 공통점은 LLM에게 오래 생각하거나 여러 역할로 토론하라고 시키는 데 있지 않다. **목적에 맞는 실행 가능한 후보를 만들고, 실제 평가 결과로 다음 후보를 선택하며, 경험과 현재 최선의 산출물을 잃지 않는 것**이다. ASI-Evolve는 지식과 실험 분석의 재사용, ASI-Forge는 영역별 실험 환경의 자동 구성, AlphaEvolve는 평가 기반 프로그램 진화와 계산 자원 운영을 특히 강조한다. [S1–S5]

이번 조사에서 실제 산업 적용 근거는 AlphaEvolve가 가장 구체적이었다. ASI-Evolve는 연구 성과·공개 구현·외부 기여가 확인되는 연구 도구이고, ASI-Forge는 이를 다른 영역으로 일반화하려는 작은 개인 프로젝트다. 이 구분은 사용자 수 통계나 모든 과제에서의 성능 순위가 아니다. [S6–S9]

첨부 스킬은 이미 상당수 연구 안전장치를 갖춘 3.1이었다. 따라서 전체 프레임워크를 이식하지 않고, **평가기 우선 설계·단계별 측정·후보 다양성·조건부 교훈·정체 의사결정**을 필요한 경우에만 추가했다. 실제 동작하는 읽기 전용 보조 도구 두 개를 구현하고 총 166개 유닛·계약·CLI 테스트를 통과했다. 실제 모델의 연구 능력·토큰·비용 개선 A/B는 수행하지 않았다.

## 2. ASI-Evolve

### 2.1 목적과 구조

GAIR의 ASI-Evolve는 아키텍처만 바꾸는 ASI-Arch의 좁은 출발점에서, 학습 데이터 구성·강화학습 알고리즘 등 코드와 평가로 표현할 수 있는 연구 문제로 범위를 확장한다. 공개 구현은 Researcher, Engineer, Analyzer와 두 종류의 저장소를 중심으로 설명된다. [S1]

| 요소 | 담당하는 일 | 해석 시 주의점 |
|---|---|---|
| Researcher | 이전 후보·관련 지식을 바탕으로 다음 프로그램/변경 제안 | 제안의 설명과 실제 효과는 별개 |
| Engineer | 외부 평가기를 호출해 실행 결과 수집 | 실행 완료와 과학적 유효성은 별개 |
| Analyzer | 결과를 다음 실험에 쓸 수 있는 교훈으로 정리 | 인과 설명은 대조 실험 없이는 가설 |
| Cognition | 외부 연구에서 얻은 사전 지식 | 문헌의 결과를 현재 프로젝트의 관측으로 바꾸면 안 됨 |
| Database | 코드·결과·분석·계보와 후보 선택 | 기록은 권한이나 새 예산이 아님 |

핵심 구조는 다음과 같다. 이것은 목적을 이해하기 위한 재구성이며 원본 전체 제어 흐름을 복제한 의사코드가 아니다.

```text
기존 연구 지식 + 이전 실험 기록
             ↓
다음 후보 설계 → 코드/실험 실행 → 결과 해석
             ↑                       ↓
             └──── 근거와 교훈 저장 ───┘
```

외부 루프는 **프로그램/가설 선택**을 개선한다. 후보가 신경망이면 내부에서 별도의 가중치 학습을 수행할 수 있다. 두 과정을 연구자 LLM이 매번 자체 가중치를 재학습하는 현상으로 혼동하지 않아야 한다.

### 2.2 효과에 관한 근거

논문은 신경망·데이터 구성·강화학습 실험을 보고한다. 또한 원 배치 문제에서 Cognition과 Analyzer 제거 실험을 각 세 차례 수행했다. 문헌 지식을 빼면 초기 탐색이 불리하고, 분석을 빼면 지속적 개선이 약해지는 결과다. 같은 과제의 샘플링 비교에서 UCB1이 MAP-Elites보다 빠른 도달을 보인 조건도 있다. **이 제한된 실험에서 얻은 결과를 모든 과제·모델에 적용되는 우열로 읽을 수는 없다.** [S2]

분석: 이 근거는 '에이전트 수가 많을수록 좋다'보다 **결과를 다음 선택에 유용한 정보로 변환하라**는 설계에 가깝다. 좋은 설명이 오류를 굳힐 수도 있으므로 관측·해석·반대 설명을 분리한 기억이 더 적절하다.

### 2.3 실제 사용과 공개 결과물

조회된 저장소 메타데이터는 **별 856개, 포크 217개**, 마지막 push는 2026-04-17이다. 별이나 포크는 실행 사용자 수가 아니다. 외부 PR에서 실행 중복 방지, 상태 복구와 안전한 역직렬화를 다루는 흔적을 확인했다. 대규모 독립 재현이나 광범위한 운영 배포까지 확인됐다는 뜻은 아니다. [S6, S9]

실제 공개 산출물로 `experiments/best/circle_packing/code_ucb17`와 관련 원 배치 프로그램이 있다. NumPy/SciPy를 이용하는 프로그램 코드이며, 모델 이름만 나열한 소개 자료가 아니다. 다만 이는 신경망 가중치가 아니다. 논문에 등장하는 모든 신경망·학습 알고리즘의 완전한 재현 묶음이나 즉시 추론 가능한 공식 체크포인트는 이번 확인 범위에서 검증하지 못했다. [S1, S10]

## 3. ASI-Forge

### 3.1 무엇을 일반화하려는가

여기서 조사한 대상은 **photodoc1960/ASI-Forge**다. GAIR의 공식 후속 이름이나 별도의 검증된 신경망 모델이 아니라, ASI-Arch를 다양한 문제에 적용하도록 확장한 개인 프로젝트다. [S3, S7]

핵심 추가 구조인 DomainBootstrapper는 다음 순서로 설정을 생성한다. [S4]

```text
영역 이해 → 지식 수집 → 제약 정의
          → 역할별 프롬프트 → 실험 환경/초기 코드 → 검증
```

Seeded는 기존 코드에서 시작하고, Genesis는 초기 코드 생성까지 포함한다. 소스 파일·인터페이스·기준선·평가·제약·지식 저장 등을 영역 설정으로 묶는다. 여러 편집 대상이 있을 때 파일 선택을 다루는 코드도 있다. [S4]

### 3.2 장점과 핵심 위험

분석: 이 시스템의 유용한 아이디어는 **새 연구 분야에 필요한 설정을 명시적 계약으로 드러내는 것**이다. '무엇을 바꿀 것인가'만 아니라 '어떻게 맞다고 판정할 것인가'가 초기 작업이 된다.

그러나 후보 코드와 평가 코드를 같은 자동화가 생성할 경우, 둘이 같은 잘못된 가정을 공유할 수 있다. 내부 검증 에이전트가 있다는 사실만으로 외부 기준에 대한 타당성이 확보되지는 않는다. 특히 정상 기준선·의도적으로 틀린 대조·필수 제약이 빠지면, 연구 루프는 의미 없는 점수를 효율적으로 높일 수 있다.

따라서 스킬에는 Forge의 모든 구성 요소를 이식하지 않고 **영역 계약과 평가기 보정**만 반영했다. 평가 오류를 고쳐야 한다면 버전을 바꾸고 양쪽 후보를 다시 비교하도록 했으며, 자동 생성 평가기를 독립적으로 맞다고 취급하지 않는다.

### 3.3 실제 사용과 결과물

공개 메타데이터는 **별 1개, 포크 0개**, 마지막 push는 2026-01-28이다. 이번 조사에서는 여러 독립 사용자의 검증된 연구 결과나 Forge 자체가 새로 만든 모델 배포를 확인하지 못했다. 이것은 비공개 사용이 없다는 주장도, 발상 자체가 무가치하다는 주장도 아니다. [S7]

프레임워크의 실제 소스는 존재한다. 다만 저장소의 106개 구조 자료는 ASI-Arch 계보의 자료라는 점을 주의해야 한다. 이를 Forge가 독립적으로 새로 발견한 106개 모델로 세어서는 안 된다. [S3, S11]

## 4. AlphaEvolve

### 4.1 목적과 작동 원리

Google DeepMind의 AlphaEvolve는 **자동으로 평가할 수 있는 알고리즘·구현을 코드 수준에서 탐색하는 시스템**이다. 사람이 초기 프로그램, 변경 가능한 부분, 평가 함수를 제공하면 프로그램 DB에서 부모와 참고 후보를 고르고, LLM이 변경을 제안하고, 평가 결과를 다시 DB에 넣는다. [S5]

주요 요소는 prompt sampler, LLM ensemble, evaluator pool, program database 및 비동기 제어다. 초기 발표는 Flash의 탐색 폭과 Pro의 제안 깊이를 함께 활용한다고 설명했다. 저비용 검사에서 불가능한 후보를 걸러 더 비싼 평가로 보내고, 단일 점수만 아니라 다양한 평가/계열을 활용하는 구조다. [S5, S12]

분석: 핵심 비용은 LLM 호출뿐 아니라 실제 후보 실행에도 있다. 따라서 좋은 시스템은 '한 답변을 얼마나 빨리 생성하는가'보다 **정해진 총예산에서 얼마나 많은 유효한 가설을 검사하고 유용한 개선을 얻는가**를 관리해야 한다. 병렬 실행은 이 목적을 도울 수 있지만, 같은 장치에서 성능 측정을 오염시키거나 공유 예산을 중복 사용하는 경우에는 역효과다.

### 4.2 사용 현황

2026-07-09 공식 발표에 따르면 AlphaEvolve는 Google Cloud의 정식 서비스가 됐다. BASF, JetBrains, Kinaxis 등 기업 활용 사례가 공개되어 있으며, Klarna는 별도의 엔지니어링 보고를 남겼다. 이는 단순 별·포크보다 구체적인 사용 근거다. 다만 총 활성 고객/사용자 수나 모든 고객에게 동일한 성과가 나는지는 확인된 통계가 아니다. [S8, S13]

### 4.3 실제 산출물과 공개 범위

Google은 발견된 데이터센터 스케줄링 규칙, TPU 회로 수정, 학습 커널 개선의 적용을 보고했다. 원 발표의 Gemini 관련 개선은 특정 커널 23% 단축과 전체 학습 시간 1% 감소이며, **Gemini 모델 전체를 AlphaEvolve가 설계했다는 뜻은 아니다.** [S12]

공개 결과 저장소 두 곳도 확인했다. [S14, S15]

| 저장소 | 실제 포함 내용 | 포함하지 않는 것 |
|---|---|---|
| `google-deepmind/alphaevolve_results` | 수학적 구성과 정답 검증 노트북 | AlphaEvolve 실행 엔진 |
| `google-deepmind/alphaevolve_repository_of_problems` | 67개 문제의 설명, 여러 문제의 초기 코드·평가 코드·최종 진화 프로그램 | AlphaEvolve 실행 엔진 |

따라서 **서비스 이용 가능**, **생성된 코드 공개**, **탐색 엔진 오픈소스**, **완성된 모델 가중치 공개**는 각각 따로 확인해야 한다. 이번에 확인한 공개 저장소도 엔진 미포함을 명시한다.

## 5. 공통적으로 중요한 것과 효과적인 구조

아래는 위 연구·코드를 바탕으로 한 설계 종합이다. 모든 항목이 동일한 조건에서 제거 실험으로 검증된 보편 법칙이라는 뜻은 아니다.

### 5.1 목적과 평가의 정합성이 최우선

평가기의 점수는 실제 목표의 대리 지표다. 모델을 복잡하게 만들거나 데이터를 미리 외우거나 평가 중에 답을 노출해서 점수가 오른 경우, 목표 능력이 좋아졌다고 주장할 수 없다. 따라서 후보 탐색 전에 **약속한 능력·비교 조건·필수 제약·평가가 말해주지 못하는 것**을 기록해야 한다.

신경망 구조 연구에서는 내부 가중치 학습과 외부 코드 탐색을 분리하고, 학습 시간·데이터·파라미터·환경 차이가 결과의 원인인지 확인한다. 알고리즘 최적화에서는 정확성·재현성·메모리·실제 입력 분포가 속도와 함께 보존돼야 한다.

### 5.2 평가 계층을 후보 편집 권한과 구별

후보 작성자는 코드를 바꿀 수 있지만, 그 후보를 판정하는 보호 데이터를 바꾸어서는 안 된다. 평가는 가능하면 후보 밖의 코드와 고정된 입력으로 수행한다. 샌드박스·쓰기 권한·작업 공간 격리가 지원되는 환경에서는 프롬프트만으로 경계를 유지하는 것보다 확실하다. 단, 실제 스킬 문서가 그런 호스트 보안 기능을 자동으로 제공하지는 않는다.

### 5.3 탐색과 확증을 분리

초기 작은 실험은 후보를 추리는 용도다. 여러 번 후보 선택에 사용한 평가 세트를 다시 보고 '독립 검증'이라고 부르지 않는다. 필요한 확인은 목표의 중요도와 불확실성에 비례해야 한다. 작은 결정적 수정마다 거대한 통계 캠페인을 요구하는 것도 낭비다.

이번 helper는 이 원리를 **단계별 measurements**로 구현했다. 같은 pilot/confirm 표시를 했다는 선언만 믿지 않고, 해당 단계의 수치가 있어야 계산한다. 단, 저장된 수치와 증거 참조가 진실한지는 실제 검증자가 별도로 확인해야 한다.

### 5.4 좋은 후보와 다른 후보를 모두 남기되 다양성 자체를 목표로 삼지 않음

좋은 부모에서 계속 변형하면 효율적이지만 좁은 한계에 갇힐 수 있다. 반대로 다양성만을 위해 형편없는 후보를 끝없이 유지하면 낭비다. 따라서 성능과 의미 있는 메커니즘 차이를 함께 고려하되, 후보 수·샘플링 정책은 문제별로 정한다. ASI-Evolve의 제한된 비교 결과도 특정 다양성 알고리즘이 언제나 가장 좋다는 주장을 뒷받침하지 않는다. [S2]

실제 개선에서는 코드/설정이 같은 중복을 새 발명과 구별하고, 불확실성을 줄이는 의도적 반복 측정은 별도 증거로 보존한다. 상충 수치가 있으면 유리한 결과만 선택하지 않고 비교 조건과 집계를 재검토한다.

### 5.5 실패 기록을 지식으로 만들되 설명을 사실로 굳히지 않음

기억은 긴 대화록의 무조건적 재주입이 아니다. “이 조건에서 무엇을 바꾸었고 어떤 관측이 있었으며, 어떤 설명은 아직 검증되지 않았는가”를 짧게 남긴다. 기존 논문, 실제 실행 결과, 가설, 반대 증거를 구별해야 다음 에이전트가 오류를 확신으로 상속하지 않는다.

요약은 원시 자료를 가리키는 색인이어야 한다. 컨텍스트를 아끼기 위해 근거를 삭제하거나, 요약만 보면서 실제 코드의 변경을 놓치면 안 된다. 이미 충분한 파일·로그가 있으면 별도의 벡터 DB는 필수 조건이 아니다.

### 5.6 역할 분리와 에이전트 분리는 다름

제안, 실행, 평가, 해석은 논리적으로 분리할 가치가 있다. 하지만 매 단계마다 다른 고급 모델을 호출해야 한다는 뜻은 아니다. 정형 검사는 코드로 처리하고, 복잡한 판단은 적절한 모델에 맡기며, 중요한 주장에는 가능한 범위에서 evidence-first 검토를 수행하는 구조가 합리적이다.

사용 중인 상위 설계자/하위 구현자가 있으면 그 설정과 권한을 유지한다. 지원되는 독립 작업과 여유 자원이 없을 때 가짜 병렬 연구를 만들거나 다른 모델로 몰래 바꾸지 않는다.

### 5.7 정체는 다음 의사결정의 신호

정체했다고 즉시 전체 목표를 포기하거나, 반대로 이유 없이 실험을 계속하는 두 방식 모두 부적절하다. 정체 시 기존 방향 개선·다른 메커니즘·편집 범위 변경·평가 오류 수정·복잡성 제거·영향받는 탐색의 보류 중 어떤 것이 유용한지 판단한다. 원래 성공 조건과 최선 산출물, 사용/예약 자원은 계속 보존한다.

## 6. 실제 시행착오와 해결 여부

| 작은 규모에서 유용했던 PASC가 커진 데이터에서 부담 | 더 단순한 후보가 선택됨 | 규모별 재평가, 제거/단순화 실험 |
| 오랫동안 개선 없이 평가 반복 | 631회 연속 무개선 경험에서 정체 한도 필요성을 보고 | 과제별 사전 정체 판단, 무근거 반복 금지 |

여기서 배운 것은 모든 문제를 더 긴 프롬프트로 해결할 수 없다는 점이다. 평가 계약, 제어 흐름, 데이터 표현, 실행 환경이 각각 자신이 맡아야 할 부분을 맡아야 한다.

## 7. 첨부 스킬 감사와 개선 계획

### 이미 있던 것

3.1은 이미 finite-goal/research-program, 실행·기록 권한 구분, 가설/반대 설명 사전등록, 네 종류 결과 판정, 비교 사전점검, 공유 예산/예약, best/active 산출물 구분, 근거 우선 검토와 재개를 갖췄다. 이를 이번에 새로 도입한 기능이라고 주장하지 않는다.

원본의 Core 계약과 `report_index.py`, `experiment_preflight.py`는 변경하지 않았다. 기존 99개 테스트 가운데 코드가 바뀐 것은 버전 문자열 기대값 한 곳뿐이다. 나머지 회귀 테스트는 그대로 사용했다. 검토 범위는 이 스킬의 계약·연결 문서·예제·보조 코드와 테스트이며, 외부 세 프레임워크 전체를 재학습하거나 완전 보안 감사한 것은 아니다.

### 개선안과 실제 구현

| 보완점 | 구현 위치 | 적용 범위 |
|---|---|---|
| 영역/평가기 우선 정의 | `references/evolution-design.md` | 새로운 영역·평가기·반복 탐색일 때 |
| 평가 cascade와 단계별 수치 | Experiment 계약, `research_portfolio.py` | 중요한 비교·비싼 실험 |
| 제약 우선, Pareto/계열 참고 | Direction 계약, portfolio helper | 여러 비교 가능한 후보가 있을 때 |
| 조건부 교훈과 반대 설명 | 새 reference와 선택형 template | 반복 연구 기록 재사용 |
| 정체의 의사결정화 | Program 계약 | 지속 연구 또는 비용 큰 탐색 |
| 필요한 규칙만 1회 인계 | `build_handoff.py` | 결정적 계약 조립이 유용할 때 |
| 이전 상태 보존 | MIGRATION, USAGE_V3_2 | 기존 계획/작업을 계속할 때 |

새 helper는 엄격한 JSON 형식, 유효성, 선행 단계, 같은 비교군, 빠진 지표, 제약, 중복/상충, 확증 식별자 및 자원 잔액을 점검한다. 그러나 **실제 모델을 학습하거나, 증거 파일을 열어 검증하거나, UCB1/MAP-Elites를 실행하거나, 사용자의 프로젝트를 자동 실행하는 도구는 아니다.** 결과의 `adoption: not_decided`와 `execution_authorized: false`가 이 경계를 명시한다.

구현 중에는 후보당 단일 metrics 구조로 pilot과 confirm을 섞을 위험을 확인했다. 출시 전에 단계별 `measurements`로 변경하고 회귀 테스트를 추가했다. 작은 수치를 큰 실험의 확인으로 재사용하지 못하도록 보완한 것이다.

## 8. OpenAI 최신 모델 가이드에 따른 최적화

요청한 정확한 URL을 읽었으며, 조회 당시 문서는 “Using GPT-5.6” 지침이었다. 모델명은 바뀔 수 있으므로 스킬 핵심에 특정 슬러그·추론 수준·API 설정을 하드코딩하지 않았다. [S16]

이번 최적화는 **조건부 로딩과 실제 단일 조립**, 권한 경계 보존, 정형 작업의 코드 처리, 필요한 근거를 잘라내지 않는 인계에 집중했다. 구체적인 런타임 변경은 현재 설정을 기준으로 별도 대표 과제에서 비교해야 한다. 가이드의 수치상 절약 사례를 이 스킬의 측정 결과로 가져오지 않았다.

실제 합성 목표로 조립한 UTF-8 크기는 Core 5,318 bytes, Core+Experiment 12,207 bytes, 6블록 연구 프로필 27,008 bytes다. 이는 **서로 다른 프로필의 크기**이며 이전 버전 대비 토큰 감소나 품질 향상을 의미하지 않는다. 기존부터 선택형 계약 원칙은 있었고, 이번에는 이를 실제 도구로 조립·검증했다.

Core는 변경하지 않아 일반 목표에 새로운 연구 규칙이 자동으로 붙지 않는다. 반대로 연구형 전체 계약은 새 기능 때문에 더 길어졌다. 필요한 조건을 보존하는 것이 무조건적 길이 감소보다 우선이다. 실제 행동 평가와 비용 절감 A/B는 미실행 상태이며 별도 프로토콜과 사례를 제공했다.

## 9. 검증 결과와 남은 한계

| 검증 | 실제 결과 |
|---|---|
| 원본 기준선 | 99 tests 통과 |
| 개선 버전 | 166 tests 통과: 기존 99 + 신규 67 |
| 후보/단계/비교군/수치/제약 helper | 42 tests 포함 |
| 인계문 조립 helper | 17 tests 포함 |
| 선택형 연구 계약 | 8 tests 포함 |
| 예제 CLI | pilot/confirm 출력과 3개 인계 프로필 실제 생성 |
| 기존 Core/보조 도구 | 원본과 동일성 확인 |
| 실제 모델 행동 | not_run: 기존 80 + 신규 16 사례는 정의만 제공 |
| 연구 생산성·토큰·가격 대비 성과 | 이번 배포에서 미측정 |

처음 한 차례의 전체 테스트 실행은 도구 실행 시간 제한에 걸려 중단됐다. 테스트 기준을 바꾸지 않고 240초 상한의 동일 스위트를 다시 실행해 **166개, 74.837초, OK**를 얻었다. 전체 로그와 호환성 정보는 ZIP 안 `tests/evidence/v3.2.0/`에 있다.

소스 존재 확인은 실제 실행 성공과 다르며, 생성 코드가 있다는 사실은 모든 논문 성능의 독립 재현을 뜻하지 않는다. 실제로 운영할 때에는 현재 호스트의 권한/격리/실행 기능과 대표 연구 과제로 확인해야 한다. 이 스킬 자체에 새 API 키, 유료 호출, 자동 배포, 프로젝트 DB 마이그레이션을 넣지 않았다.

## 10. 사용 및 마이그레이션

기존 스킬 폴더를 백업한 뒤 ZIP의 `goal-planner/`를 기존 설치 위치에 반영한다. 여러 버전이 동시에 검색되지 않게 한다. 사용자 수정이 있다면 덮어쓰는 대신 병합한다. 현재 GOAL_PLAN, 연구 상태, 최선/활성 산출물, 실행 중 작업, 비용/예약, 실패 기록은 재초기화하지 않는다.

일반 계획은 이전처럼 사용한다. 반복 후보 탐색이 필요한 요청에는 “평가기/필수 제약/편집 범위를 먼저 정의하고, 단계별 평가와 다른 메커니즘·정체 시 결정을 포함하라”고 목적과 함께 전달할 수 있다. 이는 여전히 계획 요청과 실제 실행 요청을 구별한다.

```bash
# 아래는 스킬 폴더 내부 기준. 외부 모델 호출/대상 프로젝트 변경 없음.
python -B scripts/research_portfolio.py --input examples/portfolio/snapshot.json --stage pilot
python -B scripts/build_handoff.py --goal-file examples/portfolio/goal.md --blocks Core,Experiment --stats
python -B -m unittest discover -s tests -v
```

실제 프로젝트의 연구 실행은 기존 승인된 작업 흐름을 이용한다. 사용자가 정한 상위/하위 모델과 지원되는 위임 제한을 유지하며 새 모델/에이전트는 자동으로 선택하지 않는다.
