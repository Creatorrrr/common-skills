# Goal Planner 3.1.0 사용 가이드

이름과 호출 방식은 `goal-planner` 그대로입니다. 새로 외울 모드나 명령을 추가하지 않았습니다. 목표·권한·기존 기록을 주면 필요한 검증만 선택하도록 보강했습니다. 특정 프로젝트·모델·학습 프레임워크·데이터셋은 요구하지 않습니다.

## 1. 설치와 교체

ZIP의 `goal-planner/` **전체 폴더**를 사용합니다. `SKILL.md`만 교체하지 않습니다.

| 환경 | 여러 프로젝트에서 쓰는 개인 경로 | 프로젝트 경로 | 호출 |
|---|---|---|---|
| Codex CLI / IDE | `~/.agents/skills/goal-planner/` | `.agents/skills/goal-planner/` | `$goal-planner` |
| Claude Code | `~/.claude/skills/goal-planner/` | `.claude/skills/goal-planner/` | `/goal-planner` |

기존 폴더는 스킬 검색 경로 **밖**에 백업하고 교체합니다. 사용자 정의는 [MIGRATION.md](MIGRATION.md)대로 병합합니다. 기존 경로가 symlink라면 먼저 실제 대상을 확인하여 중복 설치나 의도하지 않은 공동 사본 덮어쓰기를 피합니다. 두 도구를 함께 쓰면 둘 다 같은 3.1.0인지 확인합니다. 원본 프로젝트의 계획·실험·성공/실패 기록은 삭제하지 않습니다.

설치 후 새 세션에서 `goal-planner`를 호출하고 실제 읽은 스킬 경로와 VERSION을 확인합니다. 패키지 교체만으로 이미 생성된 `GOAL_PLAN.md`나 실행 중 세션에 복사된 계약은 자동 갱신되지 않습니다. 아래 마이그레이션 요청으로 현재 계획도 필요한 만큼 수정합니다.

원본 배포 문서의 경로와 호출은 2026-09-22에 확인한 [OpenAI 공식 문서](https://developers.openai.com/codex/skills/)와 [Claude Code 공식 문서](https://code.claude.com/docs/en/skills)에 근거합니다. 관리 정책·호스트 버전에 따라 로딩이 제한될 수 있습니다. 원본 배포의 검증과 이 작업본의 로컬 통합 결과는 [VALIDATION.md](VALIDATION.md)에 구분해 기록합니다.

## 2. 기존 프로젝트의 계획을 먼저 갱신하기

이전 버전으로 계속 연구 중이었다면 아래 요청부터 사용합니다. 검토 단계에서는 새 실험을 돌리지 않습니다.

```text
/goal-planner
현재 GOAL_PLAN.md와 관련된 최근 결과·실패 기록·실행 코드를 확인하고,
새 스킬의 검증 원칙을 반영하도록 계획 파일을 수정해줘.

원래 최종 목적, 완료 기준, 현재 목표 모델, 승인 범위, 실패 이력,
검증된 최선 산출물과 사용·예약·남은 예산은 보존해줘.

중요 비교에는 문서상 비교군과 실제 구성·동작을 대조하는 최소 점검,
후보-비교군의 실제 변경 요인과 결론의 범위,
실패 뒤 진단과 승격 확증의 구분,
중요 결과의 증거 우선 검토를 반영해줘.
이미 존재하는 검증·기록 경로는 재사용하고 작은 작업에 새 인프라를 강제하지 마.

이번에는 GOAL_PLAN.md만 수정하고 실제 구현·실험·인덱스 갱신은 시작하지 마.
기존 계약과 모순되는 내용은 어떤 조항을 어떻게 바꿨는지 정리해줘.
```

Codex에서는 첫 줄을 `$goal-planner`로 바꿉니다. 파일을 수정하기 전에 검토안만 받으려면 “계획 파일을 수정해줘”를 “수정안을 응답으로 보여줘”로 바꾸면 됩니다.

## 3. 지속적인 자율 연구를 맡기기

하나의 목표만 반복하는 `finite-goal`과, 다음 이정표 선택도 위임하는 `research-program`은 다릅니다. 아래는 지속 연구를 위한 예시입니다. 최초 사용에서는 연구 주제·목표·권한·자원 조건을 실제 상황에 맞게 넣습니다. 이미 제시한 정보는 반복해서 적을 필요가 없습니다.

```text
/goal-planner
이 프로젝트의 최종 목적과 기존 증거를 바탕으로 지속 연구용 GOAL_PLAN.md를 작성하고,
이미 승인된 실행 범위 안에서 연구를 진행해줘.
그 범위 안에서 다음 이정표를 선택하는 것도 위임한다.

가설 수립 → 필요한 조사 → 설계 → 구현 → 제한 실험 → 검증 → 결과 기록을 반복해줘.
현 구조를 유지하는 것이 목표는 아니며, 중요한 가정이 반증되면 근거 있는 대안을 비교해줘.
다만 사용자가 명시한 결과·제약·외부 계약은 유지해줘.

프로젝트의 기존 개발·실험 권한과 자원 한도를 적용해줘.
새 목표나 세션으로 넘어가도 기존 지출·예약·실패·평가 노출을 이어받아줘.
추가 유료 자원, 배포, 운영 데이터 변경은 별도 승인 없이 하지 마.
실험과 재개 상태는 기존에 승인한 기록 경로에 남겨줘.
기록 경로 승인이 없다면 먼저 세션에 남기고 영속 저장했다고 표현하지 마.

비싼 비교 전에 실제 구성·동작과 비교 의미를 확인해줘.
실패 뒤에는 어떤 결과가 다음 결정을 바꾸는지 먼저 정한 최소 진단만 수행해줘.
중요 결론은 원시 결과·코드·원래 기준부터 검토하고, 작성자의 해석과 나중에 대조해줘.

최신 후보와 검증된 최선을 구분하고,
각 경계에서 새로 확인·기각된 주장, 남은 핵심 능력, 실제 사용량, 다음 판단을 보고해줘.
실제 자원·권한·필수 의존성 한계에서는 현재 상태와 재개 조건을 기록하고 멈춰줘.
```

계획만 필요하면 첫 문장의 실행 요청을 빼고 “이번에는 계획만 작성하고 실행하지 마”라고 명시합니다. 한 목표 달성 후 멈추려면 다음 이정표 위임 문장을 빼고 “이번 목표가 끝나면 별개 목표를 자동 시작하지 마”라고 합니다. 단순 수정에는 상세 연구 프롬프트를 쓸 필요가 없습니다.

이 스킬은 반복 연구 **계약**을 작성합니다. 실행기·스케줄러·세션 재호출을 제공하지 않습니다. 실제 반복·위임·자동 재개는 사용 중인 호스트가 제공하고 승인된 기능으로만 가능합니다.

## 4. 중간 결과를 별도로 검증하기

가능하면 구현 세션의 결론을 그대로 이어받지 않은 별도 세션에서 사용합니다. 별도 세션이 없으면 같은 세션의 재검토로 수행할 수 있지만 독립 검증이라고 부르지는 않습니다.

```text
/goal-planner
현재 주요 실험 결론을 검토해줘. 이번 요청은 읽기 전용이며 파일 수정·실험 실행은 하지 마.

먼저 원래 질문과 판정 기준, 실제 구성 코드, 비교군 초기 조건,
상태 공유·초기화 동작, 원시 결과와 실패 기록을 확인해줘.
이 자료만으로 무엇을 말할 수 있고 무엇을 말할 수 없는지 먼저 판단해줘.
그 뒤 기존 보고서의 결론과 대조해줘.

각 지적에는 근거 경로, 주장에 미치는 영향, 필요한 최소 수정이나 판별 실험을 적어줘.
현재 코드가 과거 실행 코드와 같은지 확인하지 못했다면 그 한계를 명시해줘.
자료 누락을 가설 반증으로 처리하지 말고, 검증하지 않은 독립 재현을 했다고 표현하지 마.
```

이 프롬프트는 독립 검토를 자동 생성하는 기능이 아닙니다. 실제 입력 순서·세션 분리·도구 권한을 확인해야 합니다. 평가 코드는 선언만으로 쓰기 금지되지 않으므로, 필요한 격리는 프로젝트의 실행기·파일 권한·CI에서 구현해야 합니다.

## 5. 평소 확인할 결과

중요 실험에서는 긴 보고서보다 다음 정도의 요약이 유용합니다. 기존 로그 안에 넣으면 충분합니다.

```text
검증할 주장 / 이 주장이 바꿀 결정:
실행 목적: 탐색 | 진단 | 승격 확증
실제 후보-비교군 차이 / 통제 조건 / 구성·동작 근거:
유효성 / 가설 판정 / 채택 / 이정표 결과:
실제로 개선된 메커니즘 / 아직 미해결인 핵심 능력:
관측값·반대 증거·한계 / 사용한 검토 방식:
신규 작업·실측 비용 / 상속 계보 / 남은 자원과 미확인:
다음 판단과 필요한 최소 증거:
```

모든 항목을 매 명령마다 채우는 형식이 아닙니다. 하나의 작은 수정에 비교군·상태·통계가 관련 없으면 생략합니다. 연구의 진전은 버전 수나 코드량보다 새로 지지·기각한 주장과 그로 인해 바뀐 의사결정으로 확인합니다.

## 6. 상위/하위 모델 분업

현재 분업을 유지할 수 있습니다. 계획에는 **설계 / 구현 / 실행·집계 / 검증**의 책임과 쓰기 소유권을 구분하되, 모델 이름은 런타임에서 정합니다. 스킬 문구만으로 모델·추론 강도·위임 도구가 설정되지는 않습니다.

가장 강한 모델은 설계뿐 아니라 핵심 구현의 의미와 결과 해석 검토에도 배치하는 방식이 적합합니다. 정형 로그·예산·테스트 집계는 기존 스크립트를 재사용합니다. 모델별 선택의 우월성이 이번 패키지에서 실험된 것은 아닙니다. 역할을 순차 수행해도 되며 다수 모델을 항상 병렬로 유지할 필요는 없습니다.

## 7. 선택적 점검 도구와 테스트

일반 사용자는 스킬을 호출하면 됩니다. 별도의 Python 실행은 필수가 아닙니다.

실험기에서 JSON 구성 비교를 사용하려면 [작동 예제](examples/preflight/README.md)를 참고합니다. `experiment_preflight.py`는 실제 구성 exporter의 출력을 검토할 수 있게 해주는 **기계적 정합성 검사**입니다. 실제 코드/동작 검토를 대신하지 않습니다. 기존 프로젝트에 동등한 검사가 있으면 그대로 씁니다.

설치 파일의 회귀 검사는 패키지 루트에서 실행합니다.

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -B -m unittest discover -s tests -v
```

실제 에이전트가 잘못된 비교를 알아채는지 보려면 [행동 평가 안내](tests/BEHAVIORAL_EVAL.md)의 새 세션 평가를 별도로 수행합니다. 자동 코드 테스트와 실제 에이전트 행동 평가는 서로 다른 검증입니다. 이번 배포에서 실제 수행한 범위는 [VALIDATION.md](VALIDATION.md)에 명시합니다.
